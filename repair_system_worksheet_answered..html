คำถามที่ 1.1

จงระบุ User Roles ทั้ง 3 ประเภท และอธิบายสิทธิ์การเข้าถึงข้อมูลของแต่ละบทบาท

1) Admin (ผู้ดูแลระบบ) — จัดการผู้ใช้และสิทธิ์, ดูใบแจ้งซ่อมทั้งหมด, มอบหมายงานให้ช่าง, แก้ไขข้อมูลที่จำเป็น, ดู Dashboard และส่งออกข้อมูล

2) Teacher (ครู/บุคลากร) — เข้าสู่ระบบ, สร้างใบแจ้งซ่อม, แนบรูปก่อนซ่อม, ดูและติดตามสถานะของงานที่ตนแจ้ง และเพิ่มความคิดเห็น

3) Technician (เจ้าหน้าที่ซ่อม) — ดูงานที่ได้รับมอบหมาย, รับงาน/เริ่มงาน, อัปเดตสถานะ, เพิ่มผลการซ่อม ค่าใช้จ่าย และรูปหลังซ่อม

คำถามที่ 1.2

จงสกัดคำนาม (Noun Extraction) จากโจทย์ความต้องการด้านบน เพื่อระบุคลาสที่ควรสร้างในระบบ (เช่น RepairRequest, User, Comment) และคำนามที่ไม่ควรสร้างเป็นคลาส พร้อมอธิบายเหตุผล

คำนามที่ควรสร้างเป็น Class / Entity

  • User — เก็บข้อมูลผู้ใช้งาน เช่น username, fullname, role และ email
  • RepairRequest — เป็นข้อมูลหลักของใบแจ้งซ่อม เช่น สถานที่ ปัญหา ความเร่งด่วน สถานะ ผู้รับผิดชอบ และค่าใช้จ่าย
  • RepairImage — เก็บรูปก่อน/หลังซ่อม เนื่องจากหนึ่งใบแจ้งซ่อมมีได้หลายรูป
  • Comment — เก็บความคิดเห็นของผู้ใช้ที่เกี่ยวข้องกับใบแจ้งซ่อม

คำนามที่ไม่จำเป็นต้องสร้างเป็น Class แยก

  • building, room, description, cost, due_date — เป็น Attribute ของ RepairRequest
  • status, problem_type, urgency — เหมาะกับ Enum หรือค่าที่ถูกจำกัดด้วย CHECK constraint มากกว่าสร้างเป็น Entity
  • Dashboard / CSV / PDF — เป็นฟังก์ชันหรือ Presentation/Service ของระบบ ไม่ใช่ข้อมูลหลักที่มีวงจรชีวิตของตัวเอง

ดังนั้น Model หลักของระบบสามารถเริ่มจาก 4 คลาส คือ User, RepairRequest, RepairImage และ Comment

คำถามที่ 2.1

จงเขียน SQL CREATE TABLE สำหรับตาราง repair_requests พร้อมกำหนด Foreign Key Constraints และ CHECK Constraints ใน SQLite

CREATE TABLE repair_requests (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    request_no TEXT NOT NULL UNIQUE,
    user_id INTEGER NOT NULL,
    building TEXT NOT NULL,
    room TEXT NOT NULL,
    problem_type TEXT NOT NULL
        CHECK (problem_type IN ('electrical','furniture','computer','aircon','other')),
    description TEXT NOT NULL,
    urgency TEXT NOT NULL DEFAULT 'medium'
        CHECK (urgency IN ('low','medium','high')),
    status TEXT NOT NULL DEFAULT 'pending'
        CHECK (status IN ('pending','accepted','in_progress','completed')),
    assigned_to INTEGER NULL,
    due_date DATE NULL,
    completion_date DATE NULL,
    cost REAL NULL CHECK (cost IS NULL OR cost >= 0),
    result TEXT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,

    FOREIGN KEY (user_id) REFERENCES users(id)
        ON UPDATE CASCADE ON DELETE RESTRICT,
    FOREIGN KEY (assigned_to) REFERENCES users(id)
        ON UPDATE CASCADE ON DELETE SET NULL
);

ควรเปิดใช้ Foreign Key ของ SQLite ด้วย PRAGMA foreign_keys = ON; เพื่อให้ Constraints ทำงานจริง

คำถามที่ 2.2

จงอธิบายความสัมพันธ์ (Relationships) ระหว่างตารางต่างๆ พร้อมระบุ Cardinality (1:1, 1:N, M:N) และอธิบายว่าเหตุใดจึงแยกตาราง repair_images ออกจาก repair_requests

  • users 1:N repair_requests ผ่าน user_id — ผู้ใช้หนึ่งคนแจ้งซ่อมได้หลายรายการ แต่ใบแจ้งซ่อมหนึ่งรายการมีผู้แจ้งหนึ่งคน
  • users 1:N repair_requests ผ่าน assigned_to — ช่างหนึ่งคนรับผิดชอบหลายงานได้ และงานหนึ่งงานมีช่างหลักได้หนึ่งคนในโครงสร้างปัจจุบัน
  • repair_requests 1:N repair_images — หนึ่งใบแจ้งซ่อมมีรูปก่อน/หลังซ่อมได้หลายรูป
  • users 1:N comments และ repair_requests 1:N comments — ผู้ใช้หนึ่งคนเขียนหลายความคิดเห็น และใบแจ้งซ่อมหนึ่งรายการมีหลายความคิดเห็น

จึงไม่มีความสัมพันธ์ M:N โดยตรงใน Schema ปัจจุบัน หากในอนาคตต้องให้ช่างหลายคนทำงานเดียวกัน ควรสร้างตารางกลาง เช่น repair_technicians เพื่อแปลงความสัมพันธ์ M:N

เหตุผลที่แยก repair_images: เป็นการทำ Normalization และรองรับ 1:N ทำให้เพิ่มจำนวนรูปได้โดยไม่ต้องสร้างคอลัมน์ image1, image2, image3 เพิ่มเรื่อย ๆ อีกทั้งยังเก็บ image_type และ uploaded_at ของแต่ละรูปได้ชัดเจน

🔧 ตัวอย่างโค้ด: คลาส RepairRequest พร้อม Type Hints

คำถามที่ 3.1

จากโค้ดข้างต้น จงอธิบายว่า:

  • หลักการ Encapsulation ถูกนำมาใช้อย่างไรใน Python (เปรียบเทียบกับ PHP)
  • เหตุใดจึงใช้ Optional[int] และ Optional[date] (Nullable Types)
  • @dataclass decorator ช่วยลดโค้ดซ้ำซ้อนอย่างไร

Encapsulation: คลาส RepairRequest รวมทั้งข้อมูลและพฤติกรรมไว้ด้วยกัน เช่น assign_to(), start_repair(), complete_repair() ทำให้การเปลี่ยนสถานะต้องผ่าน Business Method แทนการแก้ค่าจากภายนอกโดยตรง ใน Python ใช้ convention เช่น _name, property และ method เพื่อควบคุมการเข้าถึง ส่วน PHP สามารถกำหนด private/protected/public ได้โดยตรงและบังคับใน Runtime

Optional: Optional[int] และ Optional[date] หมายถึงค่าชนิดนั้นหรือ None เหมาะกับข้อมูลที่ยังไม่มีในตอนสร้างใบแจ้งซ่อม เช่น assigned_to และ due_date ซึ่งจะมีค่าหลังจาก Admin มอบหมายงานแล้ว

@dataclass: ช่วยสร้าง __init__(), __repr__() และ __eq__() ให้อัตโนมัติจาก attributes จึงลด Boilerplate และทำให้ Model อ่านง่ายขึ้น

คำถามที่ 3.2

จงเขียน Python Function สำหรับสร้างรหัสใบแจ้งซ่อมอัตโนมัติ (Format: RP-YYYYMM-XXX เช่น RP-202609-001) โดยใช้ datetime และ str.zfill()

from datetime import datetime

def generate_request_no(sequence: int) -> str:
    now = datetime.now()
    year_month = now.strftime("%Y%m")
    running_no = str(sequence).zfill(3)
    return f"RP-{year_month}-{running_no}"

print(generate_request_no(1))
# RP-202609-001 (ถ้ารันในเดือน 09/2026)

ในระบบจริง sequence ไม่ควรรับจากผู้ใช้โดยตรง แต่ควร Query เลขลำดับล่าสุดของเดือนจากฐานข้อมูล แล้วเพิ่มอีก 1 พร้อมตรวจสอบ UNIQUE เพื่อป้องกันเลขซ้ำ

คำถามที่ 3.3

จงอธิบาย State Transition ของ status ในคลาส RepairRequest ว่าเปลี่ยนจาก pending → accepted → in_progress → completed ได้อย่างไร และเหตุใดจึงต้องมีเงื่อนไขตรวจสอบใน method start_repair() (เปรียบเทียบกับหลักการ State Pattern)

State Transition ที่ถูกต้องคือ pending → accepted → in_progress → completed

  1. สร้างใบแจ้งซ่อมใหม่ → pending
  2. Admin มอบหมายช่างด้วย assign_to() → accepted
  3. ช่างกดเริ่มซ่อมด้วย start_repair() → in_progress
  4. ช่างบันทึกผลด้วย complete_repair() → completed

เงื่อนไขใน start_repair() มีไว้ป้องกัน Transition ที่ผิด เช่น ข้ามจาก pending ไป in_progress โดยยังไม่มีผู้รับผิดชอบ หลักการนี้คล้าย State Pattern เพราะพฤติกรรมที่อนุญาตขึ้นกับ State ปัจจุบัน แต่ตัวอย่างยังเป็นแบบง่ายที่ใช้ Enum + Guard Condition; หากระบบซับซ้อนขึ้นสามารถแยกแต่ละ State เป็นคลาสได้

from flask import render_template, request, redirect, url_for, flash, abort
from flask_login import login_required, current_user

@app.route("/repair/create", methods=["GET", "POST"])
@login_required
def create_repair():
    if current_user.role not in ("teacher", "admin"):
        abort(403)

    if request.method == "POST":
        building = request.form.get("building", "").strip()
        room = request.form.get("room", "").strip()
        problem_type = request.form.get("problem_type", "")
        urgency = request.form.get("urgency", "medium")
        description = request.form.get("description", "").strip()

        allowed_types = {"electrical", "furniture", "computer", "aircon", "other"}
        allowed_urgency = {"low", "medium", "high"}

        if not building or not room or not description:
            flash("กรุณากรอกข้อมูลที่จำเป็นให้ครบ", "error")
            return render_template("repair_create.html")

        if problem_type not in allowed_types or urgency not in allowed_urgency:
            abort(400)

        repair = RepairRequestModel(
            request_no=create_request_no(),
            user_id=current_user.id,
            building=building,
            room=room,
            problem_type=problem_type,
            urgency=urgency,
            description=description,
            status="pending",
        )

        db.session.add(repair)
        db.session.commit()

        flash("แจ้งซ่อมสำเร็จ", "success")
        return redirect(url_for("repair_detail", id=repair.id))

    return render_template("repair_create.html")

from flask_login import login_user, logout_user, login_required, current_user
from werkzeug.security import check_password_hash

app = Flask(__name__)
app.config["SECRET_KEY"] = "CHANGE-THIS-IN-ENV"
login_manager.init_app(app)

@login_manager.user_loader
def load_user(user_id):
    return db.session.get(User, int(user_id))

@app.route("/login", methods=["GET", "POST"])
def login():
    if request.method == "POST":
        username = request.form["username"].strip()
        password = request.form["password"]

        user = User.query.filter_by(username=username).first()

        if user and check_password_hash(user.password_hash, password):
            login_user(user)
            return redirect(url_for("dashboard"))

        flash("ชื่อผู้ใช้หรือรหัสผ่านไม่ถูกต้อง", "error")

    return render_template("login.html")

@app.route("/logout", methods=["POST"])
@login_required
def logout():
    logout_user()
    return redirect(url_for("login"))

from pathlib import Path
from uuid import uuid4
from werkzeug.utils import secure_filename

UPLOAD_DIR = Path(app.root_path) / "static" / "uploads"
ALLOWED_EXTENSIONS = {"jpg", "jpeg", "png", "gif"}
app.config["MAX_CONTENT_LENGTH"] = 5 * 1024 * 1024

def save_image(file_storage) -> str:
    original = secure_filename(file_storage.filename or "")
    if not original or "." not in original:
        raise ValueError("Invalid filename")

    ext = original.rsplit(".", 1)[1].lower()
    if ext not in ALLOWED_EXTENSIONS:
        raise ValueError("Unsupported file type")

    UPLOAD_DIR.mkdir(parents=True, exist_ok=True)
    filename = f"{uuid4().hex}.{ext}"
    file_storage.save(UPLOAD_DIR / filename)
    return f"uploads/{filename}"

🔍 ข้อสงสัยที่พบบ่อย (Frequently Asked Questions)

รวมคำถามที่นักศึกษามักสงสัยในการวิเคราะห์และออกแบบระบบแจ้งซ่อมโรงเรียน (Python Edition) พร้อมแนวคำตอบเพื่อทบทวนความเข้าใจ

❓ Q1: ทำไมต้องใช้ Enum class สำหรับ RequestStatus และ ProblemType แทนการใช้ string ธรรมดา?
แนวคำตอบ: การใช้ Enum จาก module enum มีข้อดีหลายประการ:
  • Type Safety: ป้องกันการป้อนค่าผิด เช่น พิมพ์ "pendding" แทน "pending" → IDE จะเตือนทันที
  • Autocomplete: VS Code / PyCharm จะแนะนำค่าที่เป็นไปได้ทั้งหมด
  • Refactoring ง่าย: เปลี่ยนชื่อค่าจากที่เดียว ทุกจุดที่ใช้จะถูกอัปเดตอัตโนมัติ
  • Self-documenting: โค้ดอ่านเข้าใจได้เองว่าระบบมีสถานะอะไรบ้าง
  • SQLite CHECK: ใช้คู่กับ CHECK IN (...) ในฐานข้อมูลได้
❓ Q2: ทำไมต้องแยกตาราง repair_images ออกจาก repair_requests? เก็บเป็น path ในตารางหลักเลยไม่ได้หรือ?
แนวคำตอบ: การแยกตารางเป็นหลักการ Normalization (1NF) เพราะ:
  • 1 ใบแจ้งซ่อม มีหลายรูป: ความสัมพันธ์เป็น 1:N (อาจมีรูปก่อนซ่อม 2 รูป, หลังซ่อม 3 รูป)
  • ยืดหยุ่น: เพิ่มรูปได้ไม่จำกัด ไม่ต้องแก้โครงสร้างตาราง
  • Query ง่าย: SELECT * FROM repair_images WHERE repair_id = ?
  • ถ้าเก็บในตารางหลัก: ต้องสร้างคอลัมน์ image1, image2, image3... ซึ่งไม่ยืดหยุ่นและเสียพื้นที่
❓ Q3: ในโค้ด Python มี Optional[int] และ Optional[date] มันคืออะไร? ต่างจาก PHP ?int อย่างไร?
แนวคำตอบ: Optional[X] จาก module typing หมายความว่า ตัวแปรนั้นสามารถรับค่าเป็น type X หรือ ค่า None ก็ได้ (เทียบเท่า X | None ใน Python 3.10+)
  • PHP: ?int (Nullable Types) - ตรวจสอบตอน Runtime เท่านั้น
  • Python: Optional[int] - เป็น Type Hint สำหรับ Static Type Checker (mypy) และ IDE
  • มักใช้กับ Attribute ที่ "อาจจะยังไม่มีค่า" ในช่วงแรก เช่น assigned_to, due_date, cost
❓ Q4: @dataclass decorator คืออะไร? ทำไมต้องใช้?
แนวคำตอบ: @dataclass (Python 3.7+) เป็น decorator ที่สร้าง __init__, __repr__, __eq__ ให้อัตโนมัติจาก class attributes
  • ลด Boilerplate: ไม่ต้องเขียน __init__ เอง (เทียบเท่า Constructor Promotion ใน PHP 8)
  • อ่านง่าย: เห็นโครงสร้างข้อมูลได้ชัดเจนในบรรทัดเดียว
  • Immutable ได้: ใช้ @dataclass(frozen=True) สำหรับ immutable objects
  • เหมาะกับ Model: ใช้แทน ORM Model ในกรณีที่ไม่ต้องการความซับซ้อน
❓ Q5: การอัปโหลดรูปภาพใน Flask ต้องระวังเรื่องความปลอดภัยอะไรบ้าง?
แนวคำตอบ: การอัปโหลดไฟล์เป็นจุดเสี่ยงสำคัญ ต้องตรวจสอบดังนี้:
  • ใช้ secure_filename(): จาก werkzeug.utils เพื่อป้องกัน Path Traversal
  • ตรวจสอบ MIME type: ใช้ python-magic ไม่ใช่แค่ request.files[].mimetype (ปลอมแปลงได้)
  • จำกัดขนาดไฟล์: ตั้งค่า app.config['MAX_CONTENT_LENGTH'] = 5 * 1024 * 1024
  • เปลี่ยนชื่อไฟล์: ใช้ UUID หรือ timestamp แทนชื่อเดิม
  • จำกัดนามสกุล: อนุญาตเฉพาะ .jpg, .jpeg, .png, .gif
❓ Q6: ทำไมต้องใช้ SweetAlert2 แทน alert() ของ JavaScript?
แนวคำตอบ: SweetAlert2 มีข้อดีกว่ามาก:
  • สวยงาม: UI ทันสมัย ปรับแต่งสี/ไอคอนได้
  • Responsive: ใช้งานได้ทั้ง Desktop และ Mobile
  • Promise-based: ใช้ async/await ได้ ทำให้จัดการ Flow ง่าย
  • มีหลายประเภท: success, error, warning, info, question
  • UX ดีกว่า: alert() ดั้งเดิมจะ block thread และดูเก่า
❓ Q7: การสร้าง PDF ใน Python ต้องใช้ Library อะไร?
แนวคำตอบ: มีหลายตัวเลือกตามความเหมาะสม:
  • WeasyPrint: แปลง HTML+CSS เป็น PDF (แนะนำสำหรับใบงานนี้ เพราะใช้ Jinja2 template เดิม)
  • pdfkit (wkhtmltopdf): ต้องติดตั้ง wkhtmltopdf แยก
  • ReportLab: สร้าง PDF จากโค้ด Python โดยตรง (เหมาะสำหรับรายงานซับซ้อน)
  • FPDF / fpdf2: เบา ง่าย เหมาะกับเอกสารไม่ซับซ้อน
  • Browser Print: ใช้ CSS @media print + window.print() (ง่ายที่สุด)
❓ Q8: Flask vs Django ต่างกันอย่างไร? ทำไมใบงานนี้เลือก Flask?
แนวคำตอบ:
  • Flask (Microframework): เล็ก ยืดหยุ่น เลือก Library เอง (SQLAlchemy, Flask-Login, Jinja2) เหมาะกับการเรียนรู้โครงสร้าง
  • Django (Full-stack): มีทุกอย่างพร้อม (Admin, Auth, ORM) แต่ซับซ้อนและ "มีวิธีทำเพียงหนึ่งเดียว"
  • เหตุผลที่เลือก Flask: นักศึกษาจะได้เรียนรู้การประกอบชิ้นส่วนเอง (DIY) ซึ่งเข้าใจสถาปัตยกรรมเว็บดีกว่า และเหมาะกับขอบเขตของใบงาน
